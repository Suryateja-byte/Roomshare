## Executive summary

The engineering discipline here is real and shows up in the places that are usually weakest. Every one of the 61 route
handlers re-derives identity from `auth()` and re-checks ownership against the DB — there is no IDOR, no route reading a
user id from the request body for authorization, no admin route guarded only by UI, and no cron route missing its secret.
All 28 non-test files that use raw SQL parameterize every user value; there is no injection anywhere. Money is `Decimal(10,2)`,
Stripe signatures are verified on the raw body, entitlements can only be minted by the webhook worker, and credit consumption is
serialized by a per-user advisory lock behind two DB unique constraints. Coordinates are rounded at every publication seam,
uploads are re-encoded through sharp to strip EXIF, and CSP is a real per-request nonce policy with `strict-dynamic`
(verified live against a production build).

The defects cluster in **three seams**, and they share a shape: the *feature is correct, the plumbing around it is not*.

1. **The paywall's idempotency key is scoped too loosely.** `contact_consumption` is unique on `(userId, clientIdempotencyKey)`
   — a key the client chooses — and `consumeContactEntitlement` checks that key *before* the correctly-scoped
   `(userId, unitId, epoch, contactKind)` lookup. One key replayed across listings unlocks unlimited message-starts and
   host phone reveals, crossing both listing and contact-kind. This is simultaneously the top revenue bug and the top
   PII-exposure bug, which is why three independent reviewers found it.
2. **Fulfillment rides a once-a-day cron.** `vercel.json` schedules exactly one cron. The Stripe webhook only *captures*
   the event; the grant is created by the outbox drain, which runs inside that daily tick — so a paying customer waits up
   to ~24h for credits they already bought. Worse, that drain sits behind `isPhase02ProjectionWritesEnabled()`, which
   defaults **off in production**; if that flag isn't set at launch, payments are captured and never fulfilled at all.
3. **Cache and CI gates that look protective but aren't.** `next.config.ts` marks the entire `/listings/*` subtree
   `public, max-age=30` with no `Vary: Cookie` — including the owner/admin render that contains the exact street address.
   CI gates on an *allow-list* of test paths, so 76 test files (every security, middleware, DB-schema and RLS test) are
   written, maintained, and never run.

Everything in group 1 and 2 is currently dormant because the paywall flags default off in production — which is precisely
the state that launch flips. Treat the P0 list as a launch checklist, not an incident list.

### P0-1. Account pre-hijacking: allowDangerousEmailAccountLinking silently merges a Google identity into an attacker-created, never-verified password account

*Auth & authorization · `src/auth.ts:250` · auth-bypass*

**Impact.** Attacker POSTs /api/register with victim@example.com and a password of their choosing; the User row is created with emailVerified:null and the verification mail is ignored by the victim. Weeks later the victim clicks "Continue with Google" for the first time — Google returns email_verified:true, the signIn callback approves, and handle-login binds the victim's Google identity to the attacker's row instead of creating a new user. The victim then builds their real account on that row (listings, conversations, saved searches, phone reveals). The attacker signs in at any time with the password they set and has full, persistent read/write access to the victim's account and private messages. No password reset is triggered, no notification is sent, and nothing in the UI distinguishes the merged account from a fresh one.

**Evidence.** src/auth.ts:250 `allowDangerousEmailAccountLinking: true,` with the comment `// SAFE: email_verified === true is enforced in signIn callback above`. The signIn callback (src/auth.ts:187-215) only checks Google's `email_verified` and `isSuspended` — it never checks whether the pre-existing row was created by an unverified credential signup. @auth/core confirms the merge is unconditional: node_modules/.pnpm/@auth+core@0.41.3/node_modules/@auth/core/lib/actions/callback/handle-login.js:231-241 `const userByEmail = profile.email ? await getUserByEmail(profile.email) : null; if (userByEmail) { if (provider?.allowDangerousEmailAccountLinking) { user = userByEmail; isNewUser = false; }` — no `emailVerified` gate, and the existing user's `emailVerified` is never set. The two enabling halves: src/app/api/register/route.ts:173-189 creates the User row immediately with `emailVerified: null` and no proof of email control; src/auth.ts:302-307 `const user = await getUser(email); if (!user) return null; if (!user.password) return null; const passwordsMatch = await bcrypt.compare(password, user.password); if (passwordsMatch) return user;` — credential login has no `emailVerified` requirement. I searched for a compensating guard in the signIn callback, the linkAccount event (src/auth.ts:61-91, which only nulls OAuth tokens), and the jwt callback; none exists.

**Fix.** Refuse the dangerous link when the pre-existing row is not proven to belong to the OAuth identity. In the signIn callback, when `account.provider === "google"`, look up the user by normalized email and if `emailVerified === null && password !== null`, either reject with an error code that forces a password-reset/verification flow, or null out `password` + set `passwordChangedAt = new Date()` (revoking the attacker's credential) before allowing the link. Independently, reject credential sign-in for users with `emailVerified === null` in `authorize()`, and consider deleting unverified registrations after the 24h token TTL so the squat window closes.

<details><summary>Adversarial verification (CONFIRMED)</summary>

I re-read every link in the chain and found no compensating guard. src/auth.ts:250 sets allowDangerousEmailAccountLinking:true; the signIn callback (src/auth.ts:187-215) checks only Google's profile.email_verified and a live isSuspended lookup — nothing about the pre-existing row's emailVerified. @auth/core 0.41.3 handle-login.js:230-241 confirms the merge is unconditional (`if (userByEmail) { if (provider?.allowDangerousEmailAccountLinking) { user = userByEmail; isNewUser = false; }`) and it never writes emailVerified on the existing row. The two enabling halves are real: src/app/api/register/route.ts:171-189 creates the User row inside the transaction with `emailVerified: null` and a caller-chosen bcrypt hash, and src/auth.ts:302-307 authorizes credential login with no emailVerified requirement (only rate-limit + Turnstile + bcrypt.compare). The linkAccount event (src/auth.ts:61-91) only nulls OAuth tokens. Note the merge is also what prevents the safe failure mode: without it, @auth/core would throw OAuthAccountNotLinked, the victim would password-reset, and password-revocation (passwordChangedAt) would evict the attacker. Post-merge the victim's row is still emailVerified:null, but the victim can resend/verify and build the account normally while the attacker's password persists. P0 stands.

</details>

### P0-2. `/listings/:path*` marks authenticated, personalized pages as `Cache-Control: public` — owner/admin renders (incl. exact address) are shared-cacheable

*Config & infra · `next.config.ts:171` · cache-poisoning-pii-leak*

**Impact.** Any shared cache keyed on URL+Vary (Vercel's Edge Network, a corporate/ISP proxy) can store the *owner's or admin's* render of `/listings/<id>` — which contains the exact street address from `getListingWithLocation`, plus owner-only controls — and serve it to anonymous visitors for 30s fresh + 120s stale. The inverse also holds: an anonymous render gets served to the owner. `/listings/<id>/edit` (owner-only listing + address) and `/listings/create` are matched by the same rule. Secondary failure: `src/lib/csp-middleware.ts:8-10` mints a **new random nonce per request** while the cached HTML carries the old one; on a shared-cache hit the fresh CSP header plus `'strict-dynamic'` blocks every script Next.js emitted, so the page silently fails to hydrate.

**Evidence.** next.config.ts:170-178:
```ts
{
  source: "/listings/:path*",
  headers: [
    { key: "Cache-Control", value: "public, max-age=30, stale-while-revalidate=120" },
  ],
},
```
This path pattern matches every page under `/listings`, not just the public detail page. `src/app/listings/[id]/page.tsx:180-201` renders session-dependent output:
```ts
const session = await auth();
const isAdmin = session?.user?.isAdmin === true;
publicDetail = await getPublicListingDetail(id, { userId: session?.user?.id ?? null, isAdmin });
isOwner = publicDetail.isOwner;
canViewExactLocation = publicDetail.isOwner || publicDetail.isAdmin;
listing = canViewExactLocation ? await getListingWithLocation(id) : publicDetail.listing;
```
and `src/app/listings/[id]/edit/page.tsx:21-38` is fully session-gated and returns the owner's `location` record (full street address).

I verified this empirically against the checked-in production build (`npx next start -p 3987`):
```
$ curl -D - http://127.0.0.1:3987/listings/create
HTTP/1.1 200 OK
Cache-Control: public, max-age=30, stale-while-revalidate=120
Vary: rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch, Accept-Encoding
```
The next.config header WINS over Next's normal dynamic-page `private, no-cache`. There is **no `Vary: Cookie`**. No guard exists elsewhere: `src/proxy.ts` never touches `Cache-Control`, and neither page sets its own.

**Fix.** Delete the `/listings/:path*` rule from `next.config.ts:170-178`. If the public detail page needs edge caching, scope it to a provably anonymous render: set `Cache-Control` inside the route only when `session === null`, use `s-maxage`/`CDN-Cache-Control` rather than `public, max-age`, and add `Vary: Cookie`. `/listings/create` and `/listings/[id]/edit` must be `private, no-store`.

<details><summary>Adversarial verification (CONFIRMED)</summary>

next.config.ts:170-178 does apply `public, max-age=30, stale-while-revalidate=120` to the whole `/listings/*` subtree, and I confirmed the override is real at the framework level, not just empirically: node_modules/next/dist/server/send-payload.js — "If cache control is already set on the response we don't override it to allow users to customize it via next.config" (`if (cacheControl && !res.getHeader('Cache-Control'))`). No `Vary: Cookie` anywhere. The nonce-mismatch secondary effect is also real — src/lib/csp-middleware.ts:7-10 mints `crypto.randomUUID()` per request while cached HTML carries a stale nonce. Holds exactly as described.

### P0-3. Stripe fulfillment runs only once per day — every paying customer waits up to ~24h for the credits they bought

*Payments · `vercel.json:6` · money-correctness*

**Impact.** User pays $4.99 for CONTACT_PACK_3 at 10:00 UTC. Stripe delivers `payment_intent.succeeded`; the event is stored PENDING. `grantEntitlementForPayment` does not run until 09:02 UTC the next day. Meanwhile `/api/payments/checkout-session` returns `fulfillmentStatus: "PENDING"` (checkout-session-status.ts:259-266) forever, so the success page spins, the paywall still says PAYWALL_REQUIRED, and the user cannot message the host they just paid to reach. This is 100% of purchases, not an edge case. Secondary effect: the daily tick is capped at `maxBatch: 50` / `maxTickMs: 9000`, so a day with >50 pending outbox rows leaves payment events unfulfilled for a further 24h.

**Evidence.** vercel.json declares exactly one schedule:
```json
"crons": [ { "path": "/api/cron/daily-maintenance", "schedule": "2 9 * * *" } ]
```
The webhook route does NOT fulfill; it only captures and enqueues: `await captureStripeEvent(event); ... return NextResponse.json({ received: true })` (src/app/api/stripe/webhook/route.ts:138-147), with the grant deferred to an outbox row (`kind: "PAYMENT_WEBHOOK"`, route.ts:57). The only thing that turns that row into an `entitlementGrant.create` is `drainOutboxOnce`, and its only scheduled caller is the daily cron: `await runTask(results, "outbox-drain", async () => { const result = await drainOutboxOnce({ maxBatch: 50, maxTickMs: 9000, priorityMax: 100 }); ... })` (src/app/api/cron/daily-maintenance/route.ts:185-192). `/api/cron/outbox-drain/route.ts` exists but is absent from vercel.json and is not delegated to by daily-maintenance. I looked for any other trigger (`grep -rn drainOutboxOnce`) — there is no `after()` hook, queue consumer, or GitHub Action that drains it.

**Fix.** Fulfill inline or near-real-time rather than relying on the daily lane. Cheapest correct fix: after `captureStripeEvent` succeeds in the webhook route, kick `processCapturedStripeEventById(stripeEvent.id)` (it is already exported and idempotent via the `processedAt` guard) in a `waitUntil`/`after()` so the 200 to Stripe is not delayed, keeping the outbox row as the retry safety net. If Vercel Hobby's 2-cron/daily limit is the constraint, that inline path is mandatory — a daily drain cannot back a payments flow.

<details><summary>Adversarial verification (CONFIRMED)</summary>

Re-verified end to end. src/app/api/stripe/webhook/route.ts:38-70 only creates the StripeEvent row + a PAYMENT_WEBHOOK outbox row (priority 20) and returns {received:true}; no after()/queue/fulfilment call. The only production consumer of that row is HANDLERS.PAYMENT_WEBHOOK -> handlePaymentWebhookEvent (src/lib/outbox/handlers.ts:660, 560-577) invoked from drainOutboxOnce, and grep -rn drainOutboxOnce shows exactly two non-test call sites: src/app/api/cron/daily-maintenance/route.ts:185-192 and src/app/api/cron/outbox-drain/route.ts:50 — the latter is documented as 'NOT registered as a dedicated Vercel cron' (route.ts:8-10) and is never fetched by daily-maintenance (its runDelegatedTask list at lines 178-215 does not include it). vercel.json has one cron, '2 9 * * *', and src/__tests__/api/cron/vercel-cron-budget.test.ts:11-15 pins that to exactly one entry. processCapturedStripeEventById (webhook-worker.ts:612) is exported but has zero callers, and /api/payments/checkout-session (route.ts:124-165) only reads Payment/EntitlementGrant and polls Stripe — it never processes the captured event. ### P0-4. Contact-credit idempotency key is client-chosen and scoped only to (userId) — one key unlocks unlimited message-starts and phone reveals

*State machines & reliability · `src/lib/payments/contact-paywall.ts:563` · authorization*

**Impact.** With `ENABLE_CONTACT_PAYWALL_ENFORCEMENT` on (the launch configuration; `phaseCutoverDefault` in src/lib/env.ts:584-588 makes it default-on outside production and it is the whole point of the subsystem), a user spends exactly one of their 2 free credits (`FREE_MESSAGE_START_CONTACTS = 2`, src/lib/payments/catalog.ts:3) on listing A with `clientIdempotencyKey: "x"`, then sends `"x"` on every subsequent `startConversation` and every `POST /api/phone-reveal` for any other listing/host. Each call finds the first row by (userId, "x"), returns `ok: true, source: "EXISTING_CONSUMPTION"`, and the conversation is created / the host's decrypted phone number is returned with no credit consumed and no `contact_consumption` row written. The same key also crosses contactKind, so a MESSAGE_START consumption pays for unlimited REVEAL_PHONE. Secondary corruption: `attachConsumptionToConversation` (contact-paywall.ts:456) then re-points that one original consumption row's `conversationId` at each new conversation, destroying the consumption→conversation audit link. Net effect: $4.99 packs and $9.99 passes are unsellable — every user gets unlimited paid contacts for free.

**Evidence.** `consumeContactEntitlement` resolves the caller's arbitrary key and short-circuits on it before any unit/kind check:
```ts
const idempotencyKey = input.clientIdempotencyKey?.trim() || `legacy:${randomUUID()}`;
const existingByIdempotency = await tx.contactConsumption.findUnique({
  where: { userId_clientIdempotencyKey: { userId: input.userId, clientIdempotencyKey: idempotencyKey } },
  select: { id: true },
});
if (existingByIdempotency) {
  return { ok: true, ...evaluation, source: "EXISTING_CONSUMPTION", consumptionId: existingByIdempotency.id };
}
```
The backing constraint omits both discriminators — `prisma/migrations/20260502070000_entitlement_state_and_contact_restoration/migration.sql:68`: `CREATE UNIQUE INDEX ... "contact_consumption_user_idempotency_idx" ON "contact_consumption" ("user_id", "client_idempotency_key")`. Contrast the sibling ledgers, which DO include the discriminator: `contact_attempts_user_idempotency_kind_idx` is `(user_id, client_idempotency_key, contact_kind)` (schema.prisma:893) and `phone_reveal_audits_user_listing_idempotency_idx` is `(user_id, listing_id, client_idempotency_key)` (schema.prisma:926).
The key is fully attacker-controlled: `src/app/api/phone-reveal/route.ts:17` and `src/app/actions/chat.ts:56` both accept `clientIdempotencyKey: z.string().trim().min(1).max(200).optional()` and pass it straight through (`chat.ts:327` → `consumeMessageStartEntitlement`, `phone-reveal.ts:406` → `consumeContactEntitlement`). No caller re-validates that the returned `EXISTING_CONSUMPTION` belongs to the same unit or contactKind — `phone-reveal.ts:410` only checks `!consumption.ok`. Grepping `src/__tests__/lib/payments/contact-paywall.test.ts` shows every test passes a fresh unique key; the reuse case is untested.

**Fix.** Scope the idempotency lookup and the unique constraint to the full operation identity. Add a migration replacing `contact_consumption_user_idempotency_idx` with `(user_id, contact_kind, unit_id, client_idempotency_key)` (or at minimum `(user_id, contact_kind, client_idempotency_key)`), and change the `findUnique` in `consumeContactEntitlement` to match on the same tuple. Additionally, after finding an `existingByIdempotency` row, assert `row.contactKind === input.contactKind && row.unitId === evaluation.unitId` and reject with 400 `IDEMPOTENCY_KEY_REUSED` on mismatch — the same replay-detection posture `withIdempotency` already applies via its `requestHash` check (src/lib/idempotency.ts:198).

## 🟧 P1 — real defects, fix before launch

### P1-1. Paid-contact idempotency is keyed only on (userId, clientIdempotencyKey), which the client chooses — replaying one key unlocks every listing for free

*Database & queries · `src/lib/payments/contact-paywall.ts:563` · authorization* *(downgraded from P0)*

**Impact.** With ENABLE_CONTACT_PAYWALL + ENABLE_CONTACT_PAYWALL_ENFORCEMENT on (the intended launch state; both default off in production today via phaseCutoverDefault at src/lib/env.ts:584-588), a user spends their one FREE contact on listing A with clientIdempotencyKey="k1", then calls startConversation({listingId: B, clientIdempotencyKey: "k1"}) for every other listing on the site. Each call hits `existingByIdempotency`, returns ok:true, and chat.ts:358 creates the conversation without creating a consumption row or spending a credit — unlimited free host contacts, and the same bypass applies to REVEAL_PHONE since consumeContactEntitlement is shared (src/lib/contact/phone-reveal.ts:402). Secondary corruption: attachConsumptionToConversation (contact-paywall.ts:447-459) repoints listing A's consumption row at the new conversation each time, destroying the restoration/refund audit trail.

**Evidence.** `consumeContactEntitlement` resolves a prior consumption using ONLY the user + a client-supplied string:

```ts
const idempotencyKey = input.clientIdempotencyKey?.trim() || `legacy:${randomUUID()}`;
const existingByIdempotency = await tx.contactConsumption.findUnique({
  where: { userId_clientIdempotencyKey: { userId: input.userId, clientIdempotencyKey: idempotencyKey } },
  select: { id: true },
});
if (existingByIdempotency) {
  return { ok: true, ...evaluation, source: "EXISTING_CONSUMPTION", consumptionId: existingByIdempotency.id };
}

## What is genuinely strong

### Auth & authorization

Auth is NextAuth v5 (beta.32) / @auth/core 0.41.3 with a JWT session strategy, Prisma adapter, Google OAuth + credentials. Authorization is deliberately *not* centralized: `src/proxy.ts` (the Next 16 middleware entrypoint) only does suspension/CSP work, and every page, route handler, and server action re-derives identity from `auth()` and re-checks ownership against the DB. That per-callsite discipline is, on the whole, very good — I audited all 61 route handlers and all 14 server-action modules and found no IDOR, no route that reads a user id from the body/query for authz, no admin route protected only by UI, no cron route missing `validateCronAuth`, and no test route reachable in production. The real problems are in the *shared* auth plumbing rather than in individual endpoints: `getToken()` in the proxy is looking for the wrong cookie name on HTTPS (so the entire live-suspension layer is inert in production), the NextAuth `authorized()` callback that both `auth.ts` and `auth.config.ts` define is dead code because nothing wires NextAuth as middleware, `allowDangerousEmailAccountLinking` combined with unverified credential registration opens a classic account pre-hijacking path, and the password-revocation design revokes the acting user's own session on a self-service password change. Token handling (hashing, TTL, atomic single-use consumption, enumeration-resistant timing) is genuinely strong and is the healthiest part of this area.

- Password-reset and email-verification tokens are never stored in plaintext: `createTokenPair()`/`hashToken()` in src/lib/token-security.ts store only SHA-256, `isValidTokenFormat()` rejects non-hex before any DB hit, and consumption is atomic — src/app/api/auth/reset-password/route.ts:185-206 deletes the token and re-checks `passwordChangedAt` inside one transaction, and src/app/api/auth/verify-email/route.ts:130-167 re-reads and re-validates the slot hash inside the transaction before `deleteMany`, so a replayed link loses the race deterministically.
- Cron authentication is done correctly where most codebases get it wrong: src/lib/cron-auth.ts:13-16 compares byte-length *before* `timingSafeEqual` (so it cannot throw), and lines 23-41 default-deny on a missing/short secret and reject placeholder values like `generate-`/`your-`/`change-in-production`. All 13 `/api/cron/**` handlers call it as their first statement.
- User enumeration is closed on both signup and reset: src/app/api/register/route.ts:157-163 runs `bcrypt.hash` even when the account already exists and returns the identical 201 body via `registrationAcceptedAfterTiming`, and src/app/api/auth/forgot-password/route.ts:93-108 pads every response to a 1000-1250ms randomized floor with the same message for existing and non-existing emails.
- The admin surface never trusts the JWT: src/lib/admin-auth.ts:31-52 re-reads `isAdmin`/`isSuspended` from the DB on every call, and every consumer uses it — all 6 admin pages, `/api/admin/verifications/[id]/documents/[kind]`, and all 11 mutating server actions in src/app/actions/admin.ts, which additionally rate-limit per admin, take `FOR UPDATE` row locks, enforce optimistic `expectedVersion`, and write `logAdminAction` audit rows.
- Conversation authorization is consistently re-derived from the DB rather than from client input: `userCanAccessConversation` (src/lib/messages.ts:40-50) requires live participant membership plus `!deletedAt` plus no per-user deletion, and it is applied on every path — /api/messages GET+markRead+send, /api/messages/realtime-token:116-119 before signing the Supabase JWT, and `sendConversationMessage` re-checks participation independently at src/lib/messaging/send-conversation-message.ts:104-110.
- Test-only surface is properly gated: src/app/api/test-helpers/route.ts:26-46 requires `VERCEL_ENV !== "production"` AND `E2E_TEST_HELPERS === "true"` AND a >=16-char timing-safe bearer token (wrapped in try/catch so a length mismatch cannot throw), returning 404 rather than 401 on failure; src/app/api/test/[...slug]/route.ts is a hard 410 stub.

### PII & privacy

Privacy is implemented as a layered contract rather than ad-hoc care, and the architecture is genuinely good: a single `logger` funnels all metadata through `redactSensitive` (regex scrubbing of emails, phones, street addresses, IPs, DB URLs, paths, SQL) before stdout; Sentry runs with `sendDefaultPii: false` plus `scrubSentryEvent`/`sanitizeSentryException` on all three runtimes; public read paths go through explicit contracts (`publicListingDetailSelect` selects only `location.city/state`, `toPublicCoordinates` snaps every published lat/lng to 2 decimals, `sanitizeMapListings` re-validates after rounding, group keys are HMAC'd to `pg1_`/`u1:` tokens); host phone numbers are AES-256-GCM encrypted at rest and only released after entitlement consumption; upload strips EXIF/GPS via sharp; and there are purpose-built hashing helpers (`hashIdForLog`, `logSafeId`) plus a `scan-public-payload-pii.js` gate. The real problems are the seams where code steps outside that pipeline. Three matter: `src/lib/email.ts` writes raw upstream Resend response bodies straight to `console.error`, bypassing redaction entirely; the contact-entitlement idempotency lookup is keyed on `(userId, clientIdempotencyKey)` with no listing/unit binding, so a client-chosen key lets one paid contact unlock unlimited host phone reveals; and the redaction denylist never covers `userId`/`email`/`phone`/`address` keys, while `logger.formatLogEntry` stamps a raw `userId` onto every single log line — a direct miss against the stated "no raw PII in logs (…IDs…)" non-negotiable that the repo's own unused `logSafeId` helper was written to solve. Overall: strong design, a handful of concrete leaks at the edges.

- Coordinate privacy is enforced at every publication seam, not just one: `toPublicCoordinates` (src/lib/search/public-coordinates.ts:11) is applied in transform.ts, v2-map-data.ts, search-doc-queries.ts, data.ts and the listing page, and `sanitizeMapListings` (src/lib/maps/sanitize-map-listings.ts:103-108) re-validates coordinates *after* rounding so near-origin points that round to null island are dropped rather than published.
- `publicListingDetailSelect` (src/lib/listings/public-detail.ts:9-48) selects only `location: { city, state }`; the full address row is fetched via a separate `getListingWithLocation` call gated on `publicDetail.isOwner || publicDetail.isAdmin` (src/app/listings/[id]/page.tsx:199-203), and `coordinates` is forced to `null` for everyone else (line 249).
- `sanitizeMetadata` in src/lib/contact/contact-attempts.ts:20-37 fails closed — it *throws* on any metadata key matching `/^(email|phone|phoneNumber|address|streetAddress|postalAddress|message|content)$/i` rather than silently dropping it, so a PII-carrying audit write cannot land unnoticed.
- Telemetry consistently hashes identifiers instead of logging them: `recordPublicAutocompletePrivacyViolation` logs only `labelHash`/`labelLength`/`queryHash`/`queryHasDigit` (src/lib/geocoding/public-autocomplete-telemetry.ts:12-23), search telemetry logs `queryHash` not the query (src/lib/search/search-telemetry.ts:165-171), and messaging uses `hashIdForLog` throughout (src/lib/messaging/cfm-messaging-telemetry.ts:16-24).
- Uploads are re-encoded through sharp specifically to strip EXIF/GPS before hitting storage, and a sharp failure *rejects* the upload rather than falling through to the raw buffer (src/app/api/upload/route.ts:257-280).
- Verification documents (government ID + selfie) are behind admin auth, 60-second signed URLs, expiry/deletion checks, per-admin rate limiting and an audit write (src/app/api/admin/verifications/[id]/documents/[kind]/route.ts:28-108).

### State machines & reliability

Booking/hold/inventory reservation has been retired (`src/lib/availability.ts` is a stub — `canReserve`, `applyInventoryDeltas`, `expireOverlappingExpiredHolds` all no-op), so the live state machines are: (1) the host listing lifecycle (ACTIVE/PAUSED/RENTED + statusReason), (2) the canonical identity/inventory/projection pipeline driven by `outbox_events`, and (3) the contact-entitlement/credit ledger (`ContactConsumption` / `EntitlementGrant` / `EntitlementState`). The listing-lifecycle transitions are genuinely well built — every host and admin path takes `SELECT ... FOR UPDATE` on `"Listing"`, re-checks ownership *inside* the lock, and CASes on `version`. The projection pipeline is also careful: source-version-guarded upserts, per-unit advisory locks before aggregation, `FOR UPDATE SKIP LOCKED` outbox claiming with a stale-IN_FLIGHT sweep, DLQ routing, and retention/compaction that is explicitly allowlisted to idempotent kinds. The weaknesses are concentrated at three seams: the contact-credit ledger's idempotency key is scoped too loosely (a client-chosen key crosses contactKind *and* unit, which is a straight paywall bypass), the cron layer wraps multi-second dispatchers in Prisma's default 5-second interactive transaction and gates all daily work on a 3-minute UTC window that Vercel Hobby cron jitter will usually miss, and several handlers do outbound network I/O with an open SERIALIZABLE transaction / without a claim, producing at-least-once side effects (duplicate emails) and lost retry bookkeeping.

- Host and admin listing-status transitions are correctly serialized: `src/app/actions/listing-status.ts:106-156` takes `SELECT ... FOR UPDATE` on the Listing row, re-reads `ownerId` inside the lock, and CASes on `version !== expectedVersion` before writing — the same pattern is repeated in `src/app/api/listings/[id]/route.ts:679-731` and in every admin moderation action (`src/app/actions/admin.ts:386, 547, 708, 1036`).
- The outbox drain claims work safely for concurrent workers: `src/lib/outbox/drain.ts:112-157` uses `FOR UPDATE SKIP LOCKED` plus a status flip to IN_FLIGHT inside one transaction, and `drain.ts:103-110` resets IN_FLIGHT rows older than 5 minutes so a killed function cannot strand events forever.
- Projection writes are source-version-ordered rather than last-writer-wins: `src/lib/projections/inventory-projection.ts:241` guards the upsert with `WHERE inventory_search_projection.source_version <= EXCLUDED.source_version`, and `src/lib/projections/unit-projection.ts:59-61` takes a per-unit `pg_advisory_xact_lock` *before* the aggregate read, with an inline comment explaining why MAX(source_version) is not a valid staleness token.
- `src/lib/outbox/retention.ts:46-49` restricts compaction to `INVENTORY_UPSERTED`/`UNIT_UPSERTED` with an explicit NEVER-ADD list covering PAYMENT_WEBHOOK, ALERT_*, IDENTITY_MUTATION and CACHE_INVALIDATE, and both delete statements re-check `status` inside the DELETE so a concurrently-claimed or re-queued row is not dropped.
- Contact restoration is properly idempotent: `src/lib/payments/contact-restoration.ts:146-158` uses `updateMany` with a `restorationState: "NONE"` compare-and-swap and returns early on `count === 0`, backed by the `contact_restorations_consumption_reason_idx` unique constraint plus a P2002 replay handler at line 222.

### Payments

The payments subsystem is a Stripe Checkout (one-time payment) → webhook → entitlement-grant pipeline. `POST /api/stripe/webhook` verifies the signature on the raw body, persists the event into `StripeEvent` (unique on `stripe_event_id`) and enqueues a `PAYMENT_WEBHOOK` outbox row in the same transaction; the actual money side effects run later in `processCapturedStripeEvent` inside a SERIALIZABLE `withActor` transaction, guarded by a `processedAt` check plus a `pg_advisory_xact_lock` on the event id. Entitlements are granted only from `payment_intent.succeeded` (never from the browser return URL), the client-facing `/api/payments/checkout-session` endpoint is strictly read-only and ownership-checked, money is stored as `Decimal(10,2)` derived from Stripe cents, and contact consumption is serialized per user with a per-user advisory lock plus two unique keys. The security fundamentals (signature, secret required, no client-priced amounts, no spoofable fulfillment) are genuinely solid. The failures are in *delivery* and *lifecycle*: the outbox drain that performs fulfillment is only scheduled once per day, so every paying customer waits up to ~24h for what they bought; the payment↔intent reconciliation fallback picks the wrong row when a user has two open checkout sessions, poisoning the sibling webhook event with a unique-constraint violation; and dispute/refund adjustment math misclassifies Stripe inquiry closures as chargeback losses and is non-idempotent once credits are consumed. Test coverage is asymmetric — `payment_intent.succeeded` is well covered, but dispute/refund lifecycle branches (`warning_closed`, replayed `refund.updated`) are not.

- Webhook signature verification is done correctly: `request.text()` gives the raw body before any parsing, `constructEvent` runs before any DB write, and a missing `STRIPE_WEBHOOK_SECRET` hard-fails with 400 rather than being dev-bypassed (src/app/api/stripe/webhook/route.ts:101-136).
- Entitlements can only be created by the webhook worker — `entitlementGrant.create` exists in exactly one place (src/lib/payments/webhook-worker.ts:377). The success-URL path (`/api/payments/checkout-session`) is read-only and double-checks `payment.userId === session.user.id` AND `metadata.userId === session.user.id` AND listing/context match before returning anything (src/app/api/payments/checkout-session/route.ts:104-122).
- No client-supplied pricing: the checkout route prices from `getStripePriceId()` env price IDs and a server-side catalog, and the webhook re-validates the charged amount and currency against `PRODUCT_CATALOG` before granting (src/lib/payments/webhook-worker.ts:251-275).
- Credit consumption is race-safe: `pg_advisory_xact_lock(hashtext('paywall:{userId}:{contactKind}'))` serializes per user, backed by two DB unique constraints — `(userId, clientIdempotencyKey)` and `(userId, unitId, unitIdentityEpoch, contactKind)` (src/lib/payments/contact-paywall.ts:558-601; prisma/schema.prisma:788-789).
- The auto-refund queue is genuinely careful about double-refunds: deterministic Stripe idempotency key `auto-refund:{paymentId}:{reason}` plus a reconcile-by-metadata lookup (`findExistingQueuedRefund`) that survives Stripe's ~24h idempotency-key window, and a stale-PROCESSING reaper so a mid-flight crash self-heals (src/lib/payments/refund-queue.ts:227-244, 300-334, 362-371).
- Payment telemetry hashes identifiers rather than logging them raw (`userIdHash`, `listingIdHash`, `unitIdHash` via `hashIdForLog`) — src/lib/payments/telemetry.ts:18-20, 59-72.

### Database & queries

The data layer is two-tiered: a Prisma-managed core (53 models) plus a set of raw-SQL-managed read models (`listing_search_docs`, `listing_search_doc_dirty`, the phase-02/03/04 projection tables) driven by an outbox + dirty-flag pipeline. Raw SQL is used heavily (28 non-test files) but the parameterization discipline is genuinely good: I traced every `$queryRawUnsafe`/`$executeRawUnsafe` call site and found **zero SQL injection** — every user-derived value goes through a `$N` placeholder, ORDER BY is built from a closed `switch`, and `src/lib/sql-safety.ts` is applied on the search/facet/projection paths. Migrations are unusually well-documented (rollback + data-safety notes on nearly every file), the enum `ALTER TYPE ADD VALUE` statements never use the new value in the same transaction, and `CREATE INDEX CONCURRENTLY` is correctly isolated into single-statement migrations. The real problems are elsewhere: one client-controlled idempotency key is used as the sole lookup key for a paid-contact consumption row, which is a straight paywall bypass; the semantic-search read path skips the host-suspension eligibility gate that every other search surface enforces; several hot/soon-hot paths have no usable index (HNSW dead due to CTE materialization, projection geo filter is a text regex, autocomplete is a leading-wildcard LIKE); and the shared `queryWithTimeout` helper sets a statement timeout equal to Prisma's own transaction budget so it can never fire cleanly. Most of the dangerous flags default off in production today, which makes these launch-blockers rather than live incidents.

- No SQL injection anywhere in the raw-SQL surface. I checked all 28 non-test files that call queryRaw/executeRaw plus a scripted scan of every `${}` interpolation inside SQL template literals: every interpolation is a `$N` index, a module constant, or a closed-switch clause. src/lib/sql-safety.ts (assertParameterizedWhereClause, joinWhereClauseWithSecurityInvariant) is genuinely applied at the search-doc, facets, projection-search and freshness-metrics call sites, and the keyset cursor builder in src/lib/search/search-doc-queries.ts:507-690 parameterizes every cursor value including NaN rejection.
- Idempotency and claim primitives are correctly built at the DB level: src/lib/idempotency.ts:143-179 uses INSERT ... ON CONFLICT DO NOTHING followed by SELECT ... FOR UPDATE inside a SERIALIZABLE transaction with retry, and src/lib/outbox/drain.ts:110-155 claims with FOR UPDATE SKIP LOCKED plus a stale-IN_FLIGHT reset — both are textbook-correct and backed by real unique constraints (IdempotencyKey_user_endpoint_key_idx, alert_deliveries_idempotency_key_key).
- Migration hygiene is above average for a project this size: prisma/migrations/20260613000000_readd_listing_booking_mode/migration.sql adds a NOT NULL column with a constant DEFAULT (metadata-only on PG11+), backfills, then adds the CHECK as NOT VALID before VALIDATE — exactly the non-blocking pattern. prisma/migrations/20260702000000_drop_dead_search_doc_partial_indexes documents *why* no replacement index is added rather than reflexively adding one.
- Money is stored correctly as Decimal(10,2) everywhere (Listing.price, payments.amount, refunds.amount, payment_disputes.amount, listing_inventories.price), and prisma/migrations/20260221000000_search_doc_price_decimal caught and fixed the one denormalized column that had been left as DOUBLE PRECISION.
- The Prisma client is configured for serverless correctly (src/lib/prisma.ts:20-41 pins connection_limit=5/pool_timeout=10, globalThis caching to avoid connection churn) and the slow-query listener at :111-121 deliberately omits `e.params` with an explicit comment that params may contain PII — that matches the project's no-PII-in-logs non-negotiable.

### Search, map & cost

The search subsystem is a three-engine stack (legacy Prisma `getListingsPaginated` → denormalized `listing_search_docs` "SearchDoc" → phase-04 `inventory_search_projection`), fronted by a single normalization seam (`src/lib/search-params.ts` → `normalizeSearchFilters`) that every route funnels through, and a versioned cursor layer (`src/lib/search/cursor.ts`) with HMAC-signed keyset/snapshot cursors. The URL→schema→SQL round-trip is genuinely disciplined: sort is allowlisted, arrays are allowlist-filtered, all user values are `$N` params behind `joinWhereClauseWithSecurityInvariant`, and the documented client invariants (component keyed by canonical `searchParamsString`, `seenIdsRef`/`seenGroupKeysRef` dedupe, `MAX_ACCUMULATED=60`, 50ms map debounce + 800ms min interval + AbortController) all hold in code. The weak spots are at the edges of that discipline: the **saved-search read path silently drops geographic bounds and lat/lng** (verified by running the parser), the **alert matcher applies no geographic constraint at all**, and cost controls are applied inconsistently — the map/count/facets routes clamp bounds spans but the list path does not, paid geocoding providers have Redis monthly caps but the Gemini embedding path has none, and the semantic "eligible page" walk re-filters an SQL-expressible predicate in JS with an O(n²) OFFSET walk that degrades exactly when inventory goes stale. Overall health: solid core, but the saved-search/alerts lane is materially broken and several cost gates are missing before launch.

- Cursor pagination is genuinely stable: `buildKeysetWhereClause` (src/lib/search/search-doc-queries.ts:505-704) uses explicit OR-chains per sort direction instead of tuple comparison, handles NULLS LAST correctly for every sort, rejects NaN cursor keys with `clause: "FALSE"`, and always terminates with a unique `d.id` tiebreaker matching `buildOrderByClause`. `ts_rank_cd` is deliberately excluded from keyset ORDER BY because the cursor cannot capture it (search-doc-queries.ts:1082-1085).
- Cursors are HMAC-signed and bound to their filter set: `encodeKeysetCursor`/`decodeKeysetCursor` (src/lib/search/cursor.ts:216-320) use `timingSafeEqual`, and `search-v2-service.ts:764-784` rejects a v2 cursor whose `snapshot.qh` (bare filter hash), engine, responseVersion, projectionVersion or embeddingVersion differs — so a cursor minted under filter set A cannot be replayed against filter set B.
- The documented map-move contract is real: `MAP_MOVE_SEARCH_DEBOUNCE_MS = 50` and `MIN_SEARCH_INTERVAL_MS = 800` (src/components/Map.tsx:1639-1640) with a trailing throttle queue at Map.tsx:3620-3641, plus viewport hysteresis (`isViewportContained`, 90% overlap), a 20-entry spatial cache with the documented 30s TTL, separate AbortControllers for the search and pan effects, and a 15s fetch timeout in src/components/PersistentMapWrapper.tsx:1003-1120.
- Snapshot page hydration cannot skip rows: `hydrateSnapshotPage` slices the FROZEN `orderedListingIds` by absolute offset and advances `nextOffset` by `listingIds.length` (not by the surviving item count), and `getSearchDocListingsByIds` re-maps results back into the requested ID order (src/lib/search/search-doc-queries.ts:1468-1470). `hydratePhase04Snapshot` does the same over `orderedUnitKeys` with an explicit comment about hole-shifting (src/lib/search/projection-search.ts:935-951).
- Test-scenario injection is correctly env-gated — `resolveSearchScenario` returns null unless `ENABLE_SEARCH_TEST_SCENARIOS === "true"` (src/lib/search/testing/search-scenarios.ts:66,345), so the `x-e2e-search-scenario` header cannot be used in production to bypass the rate limiter that `/api/map-listings` skips for scenarios.

### Frontend correctness

The frontend is a Next.js App Router app where nearly all heavy surfaces are client components hydrated from server-rendered props (search, map, messages, listing detail, create-listing). Architecture boundaries hold: I scanned every `'use client'` file and none import `@/lib/prisma`, `@/lib/db`, or `server-only`; business rules that matter (paywall, message send, listing create) are enforced in server actions/route handlers with the client only rendering affordances. Async correctness in the search/map stack is unusually disciplined — `SearchResultsClient` and `PersistentMapWrapper` both sequence responses with AbortControllers plus a `queryHash`/`latestRequestRef` comparison before committing state, and `Map.tsx` centralizes cleanup of ~12 timers, the maplibre `sourcedata` listener and the WebGL context listeners in one unmount effect. The weak areas are the messaging surface and shared UI primitives: the `/messages` list-pane send path has no error handling or in-flight guard (unlike the near-identical `ChatWindow`), all chat timestamps are formatted with the *runtime's* timezone during SSR so they hydrate wrong, `useBodyScrollLock` manipulates `document.body` in an app whose body has `overflow:hidden` (so it locks nothing), and the listing-detail contact CTA renders from an optimistic client fallback that makes the paywall modal fail to open. Client-side search failures are also swallowed with no user-visible error surface, which violates the project's "always handle empty/error/loading" rule.

- Client/server boundary is clean: scanning every file with a `'use client'` directive for imports of `@/lib/prisma`, `@/lib/db`, `@prisma/client` runtime, or `server-only` returned zero hits — no client component reaches the DB, and business rules stay server-side (e.g. `ContactHostButton.handleContact` relies on `startConversation` returning `PAYWALL_REQUIRED` rather than deciding locally, src/components/ContactHostButton.tsx:126-135).
- Genuinely race-safe client search: `SearchResultsClient` aborts the superseded request, then double-gates commits on both `data.meta.queryHash !== requestQueryHash` and `latestQueryHashRef.current !== requestQueryHash` before any setState (src/components/search/SearchResultsClient.tsx:463-479), and emits a `search_map_list_mismatch_total` metric on rejection. `PersistentMapWrapper` mirrors this with `latestMapRequestRef` (src/components/PersistentMapWrapper.tsx:787-803).
- Create-listing submit is idempotency-correct: a synchronous `isSubmittingRef` guard precedes the async work, and the `X-Idempotency-Key` is deliberately *preserved* on network errors ("a network error may mean the request committed but its response was lost") while regenerated only on definitive 4xx rejections (src/app/listings/create/CreateListingForm.tsx:636-638, 723-730, 778-786).
- Map lifecycle cleanup is thorough for a 4944-line component: one `useEffect(..., [])` clears all 12 timer refs, removes the maplibre `sourcedata` handler, and invokes `webglCleanupRef` which unbinds the `webglcontextlost`/`webglcontextrestored` canvas listeners (src/components/Map.tsx:3103-3169, 4290-4299); `onLoad` also removes the previous `sourcedata` handler before re-registering to avoid duplicates across style reloads (src/components/Map.tsx:4209-4218).
- Modal and sheet keyboard support is real, not cosmetic: `FilterModal` has `role="dialog"`/`aria-modal`, an Escape handler that respects `defaultPrevented` so Radix Selects can consume it first, and a `FocusTrap` with focus restore (src/components/search/FilterModal.tsx:165-174, 202; src/components/ui/FocusTrap.tsx:90-97), and the mobile sheet drag handle is a `role="slider"` with ArrowUp/Down/Home/End/Enter equivalents (src/components/search/MobileBottomSheet.tsx:464-500).

### Tests & CI gates

The suite is large (526 Jest files, ~208 Playwright specs) and in places genuinely good: cron auth, password-reset TOCTOU races, and Stripe amount-tampering all have real, meaningful tests, and external HTTP is uniformly mocked behind adapters. The architecture problem is the CI wiring, not the tests themselves: `ci.yml` gates the merge on an *enumerated allow-list* of six `--testPathPatterns` jobs, so 76 test files — every file under `src/__tests__/security/`, `middleware/`, `db/`, `schema/`, `edge-cases/`, `scripts/`, `launch/`, plus the colocated `src/lib/search/**/__tests__/` — are written, maintained, and never executed by any workflow. Two of the gates that look like they enforce the project's non-negotiables are structurally incapable of failing: the PII scan runs against a hand-written clean fixture, and the Playwright skip audit invokes a script whose only `exit 1` is behind a `--ci` flag the workflow doesn't pass. Within the tests that do run, the money-critical path has a specific hole — no test anywhere exercises the duplicate-entitlement-grant guard on Stripe webhook redelivery. Concurrency claims are largely unbacked: outbox `FOR UPDATE SKIP LOCKED` claim exclusivity and contact-entitlement double-spend are only ever tested against jest mocks called sequentially, and the one real-DB concurrency test lives in a directory CI skips. Overall health: the tests are better than the gates, and the gates are what protect main.

- All 13 cron routes have route-level tests and the shared authenticator is unit-tested (src/__tests__/api/cron/*.test.ts plus src/__tests__/lib/cron-auth.test.ts) — CRON_SECRET verification is a commonly-missed authz surface that is genuinely covered here.
- Password reset has real lifecycle and TOCTOU coverage, not just happy path: src/__tests__/api/auth/reset-password.test.ts:367 ("returns a 400 when the token was invalidated after validation but before delete") and :403 ("returns a 400 when a newer password change wins during the transaction") pin the exact races that break single-use tokens.
- External services are consistently mocked at the adapter seam rather than at `global.fetch` — e.g. src/__tests__/lib/geocoding/nominatim-api.test.ts:1-4 mocks `@/lib/fetch-with-timeout`; a repo-wide grep found no test issuing a real outbound HTTP request.
- Real-Postgres (PGlite) fixtures exist for identity, outbox handlers, and projections, and the concurrency limitation is documented honestly rather than papered over — src/__tests__/db/phase01-advisory-lock-contention.test.ts:10-15 states PGlite is single-connection so the test proves uniqueness but not true lock contention.
- playwright.config.ts contains two real anti-flake wins that most repos miss: `serviceWorkers: "block"` (line 112, with a comment explaining that sw.js was silently bypassing page.route() mocks in CI production builds) and `forbidOnly: !!process.env.CI` (line 128).

### Config & infra

Configuration and infra here are unusually mature for a pre-launch app: CSP is genuinely enforced per-request with a fresh nonce from `src/proxy.ts` (I confirmed live against a production build that the nonce is emitted and Next applies it to its own preload/link headers), `frame-ancestors 'none'` / `object-src 'none'` / `base-uri` / `form-action` are all locked down, HSTS+nosniff+Referrer-Policy are set, `src/lib/env.ts` hard-fails production boot on missing Turnstile and on the E2E search-scenario seam, `instrumentation.ts` actually calls `getServerEnv()` so that validation runs, there are zero TS/ESLint build escape hatches, and no credentials are committed. Rate limiting is broad (100+ named buckets) and correctly fails *closed* for the LLM chat path. The weak spots are all in the seams: a `next.config.ts` header rule marks every `/listings/*` page — including the authenticated owner/admin detail render and the session-gated `/edit` and `/create` pages — as `public, max-age=30` with no `Vary: Cookie`, which I verified empirically; the image optimizer allowlists a `*.googleusercontent.com` wildcard that turns `/_next/image` into an unauthenticated open image proxy; `LOG_HMAC_SECRET` is documented "[REQUIRED in PROD]" but has no production enforcement and its consumer fails open; client-side Sentry is wired to a file that is never bundled; and `phaseCutoverDefault` inverts ~15 feature-flag defaults between test/dev and production so the production code path is the one the test suite never exercises. Overall health: solid foundation, but the caching rule is a launch-blocker.

- CSP is real, not theatre: `src/lib/csp.ts:69-98` builds a nonce + 'strict-dynamic' policy with `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`, and `src/proxy.ts:32-37` feeds it back via the request `content-security-policy` header so Next.js picks up the nonce. I ran `next start` against the existing production build and confirmed the emitted header carries `'nonce-e1d8e56f…' 'strict-dynamic'` and that Next stamped the same nonce onto its `link` preload headers. Both third-party scripts (Turnstile, Google Maps) are injected dynamically from already-trusted code (`src/lib/googleMapsUiKitLoader.ts:176`), so 'strict-dynamic' does not break them.
- Rate limiting fails closed where money is at stake: `src/lib/rate-limit-redis.ts:410-428` and `:468-477` return `{success:false}` for the LLM chat endpoint when Upstash is unconfigured or the circuit breaker trips, rather than falling open; `src/lib/rate-limit.ts:199-224` degrades to a capped (10k-entry, LRU-evicting) in-process limiter on DB failure instead of allowing everything.
- No secrets are committed. Grepping every tracked non-binary file for `sk_live_`/`AIza…`/JWT/private-key/`postgres://user:pass@` patterns yields only localhost dummies (`.github/workflows/ci.yml:75,227`, `jest.env.js:5`). `.gitignore:41-44` ignores `.env*` (allowlisting only `.env.example`) and `*.log`, and the ~7MB of root dev-server logs are correctly untracked (`git check-ignore` confirms `.gitignore:44` catches them).
- Zero build escape hatches: `next.config.ts` has no `typescript.ignoreBuildErrors` or `eslint.ignoreDuringBuilds`, `tsconfig.json:9` sets `"strict": true`, and there is exactly **one** `@ts-expect-error` in all non-test `src/` code (`src/lib/email.ts:195`). The handful of `eslint-disable` comments are narrowly scoped with justifying comments.
- `src/app/api/upload/route.ts` gets file upload right end-to-end: 5MB size cap checked before buffering, declared-MIME allowlist, magic-byte verification (`validateMagicBytes`), full re-encode through sharp to strip EXIF/GPS, extension derived from the *validated* MIME via `MIME_TO_EXTENSION` (never from the user filename), storage path scoped to `${folder}/${session.user.id}/`, and DELETE gated on a strict `path.startsWith("${folder}/${session.user.id}/")` prefix. Verification documents (`src/app/api/verification/upload/route.ts`) go to a private bucket read only through an admin-authed, audit-logged, 60s signed URL with `Cache-Control: no-store` (`src/app/api/admin/verifications/[id]/documents/[kind]/route.ts:108-110`).
